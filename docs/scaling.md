# Масштабирование и конфигурация

## Реализованный путь запроса

`карточка → Qwen/Pydantic AI → поисковые needs → embeddings → CandidateRetriever
→ ограниченный пул → BGE → личный ранкер → SlatePolicy → сохранённая выдача`.

Отраслевых таблиц вида «пекарне всегда показывать X» в рабочем пути нет.
Содержимое потребностей берётся из профиля, а подходящие предложения — из
векторов и направлений связи. Категории в `scripts/mixed_market_check.py` —
только локальная проверочная выборка. Значения по умолчанию остаются явной
политикой продукта, а не выдаются за обученные параметры.

### Поиск кандидатов

`src/business_match/retrieval.py` задаёт интерфейс `CandidateRetriever` и реализацию
`ExactRetriever`. Она читает каталог keyset-страницами по ID, применяет фильтры
региона/города в SQL, считает близость блоками NumPy и хранит top-K компаний каждой
роли в ограниченных кучах. Граф, карточки товаров и ранкер работают уже над этим пулом.
В `Engine` можно передать другой retriever; контракт возвращает компанию, роль,
совпавшую потребность, документ и semantic score.

Параметры памяти: `RETRIEVAL_CLIENT_BATCH_SIZE`, `RETRIEVAL_DOCUMENT_BATCH_SIZE`,
`RETRIEVAL_QUERY_BATCH_SIZE`, `CANDIDATE_LIMIT`. На странице всё ещё декодируются
полные JSON карточек, включая их документы. Большой каталог одного клиента также
занимает память целиком. Keyset-чтение не является консистентным snapshot всего
каталога при параллельных обновлениях.

Exact backend остаётся линейным по числу документов: он **не ANN**, даже при
ограниченной памяти. Дальнейший шаг для большого каталога — индекс документов
с фильтрами, идентификаторами и ревизиями, ANN-кандидаты и exact reranking.
Для подключения через интерфейс нужно проверить recall, фильтры, удаления,
обновления и направление buyer/supplier против точного эталона.

### Обучение и составление ленты

- Размер проекции и seed задаются `CONTENT_DIMENSIONS` и `CONTENT_PROJECTION_SEED`.
  Список признаков формируется из схемы; числовое смещение 14 удалено из вычислений.
- `RANKER_MAX_OBSERVATIONS` ограничивает личное состояние. Коэффициенты модели
  вычисляются один раз на запрос, а не повторно для каждого кандидата.
- В разнообразии нет матрицы размером N×N: после выбора карточки рассчитывается
  один вектор близостей. Память растёт как N×D, время — как N×D×длина ленты.
- Награды, baseline, окна истории/скрытия, затухание, веса и priors графа задаются
  через `Settings`/переменные окружения. Все добавленные параметры есть в `.env.example`.
- Версия личного ранкера включает fingerprint схемы, модели/provider и настроек
  обучающих меток. Несовместимое состояние не используется; feedback по старой
  версии выдачи отклоняется. Это сброс совместимости, не миграция истории.
- Изменения конфигурации применяйте перезапуском сервиса. Настройки не являются
  механизмом горячего переключения; старые агрегаты графа автоматически не пересчитываются.

## Диагностика

В `diagnostics` ответа добавлены `retrieval_backend`, `retrieval_ms`, `rerank_ms`,
`ranking_ms`, `slate_ms`, `engine_total_ms`. Последний включает работу engine и
сохранение выдачи, но не ожидание API-lock, сериализацию ответа и сетевую задержку.
Метрики предназначены для поиска узкого этапа, не являются замером RPS или SLA.

## Проверки

```powershell
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe -m ruff check .
.venv\Scripts\python.exe scripts/mixed_market_check.py
.venv\Scripts\python.exe scripts/synthetic_check.py --per-category 300
.venv\Scripts\python.exe scripts/synthetic_check.py --per-category 1000
```

Регрессионный эталон сравнивает IDs, scores и совпавшие документы с независимым
полным перебором: все четыре роли, feed/search, разные размеры блоков, исключения
и география. Отдельно проверяются обновления карточек, несовместимые размерности,
смена схемы обучения и ограничение числа наблюдений.

Прогон 26 ноября 2026 (`local_experiments/20261126-074426`): **1 202 компании,
18 проверок**, feed около **1.30–1.34 с**, запрос с фильтром около **0.86 с**.
Предыдущий вариант в той же локальной серии: около **1.57–1.72 с** без фильтра.
Это ориентировочное сравнение отдельных прогонов, не статистический benchmark.
Смешанный сценарий `20261126-074810-mixed`: **28 проверок прошли**.
Модели здесь — HTTP-моки, SQLite локальная. Полные отчёты остаются вне Git.

Больший прогон `20261126-074852`: **4 002 компании, все 18 проверок прошли**.
Без фильтра feed **4.17–4.43 с**, с фильтром **2.62 с**. Упаковка после контактов:
top-10 **7 → 10**, top-50 **27 → 30**, средняя позиция **24.26 → 16.00**.
Рост времени примерно пропорционален каталогу: ограничение памяти работает
архитектурно, но низкая latency на больших объёмах требует индексного backend.

## Границы эксплуатации

Сервис пока запускается **с одним worker**. API-limiter и блокировка обучения
внутрипроцессные; синхронная SQL/CPU-работа может блокировать event loop.
Замена SQLite на PostgreSQL сама по себе не делает несколько worker безопасными.
Для горизонтального запуска нужны транзакционная координация обновлений пользователя
и общих рёбер графа, общий лимитер внешних API и вынос тяжёлой индексации в очередь.
Такой запуск в этом изменении не реализован и не заявлен протестированным.

История событий фильтруется по времени на стороне SQL, но JSON-поле времени
не имеет отдельного индекса. Raw events и slates требуют политики хранения;
личный лимит наблюдений не ограничивает размер этих таблиц.

Настройки убирают скрытые бизнес-константы, но не заменяют калибровку на реальных
данных. Нет гарантии, что относительный порог отделит нерелевантные предложения,
если все кандидаты плохие. Нет доказательства качества настоящей Qwen/BGE или
готовности к миллионам компаний по результатам этого локального прогона.

# ML-логика MVP

## Представление бизнеса

Похожесть предложений сама по себе даёт конкурентов. Основное направление:
**потребность зрителя → предложение другой компании**, а не профиль → профиль.

LLM формирует summary, offers, needs. Каждая need имеет роль, важность и признак
`explicit|inferred`; предположения слабее фактов. Сегмент берётся из витрины,
LLM не изобретает отдельную таксономию. Профиль строится при изменении семантических
полей; в LLM поступает ограниченная, разнообразная по категориям выборка товаров.
Все доступные товары индексируются отдельно, независимо от выборки в LLM.

Needs кодируются как Qwen retrieval queries, offers/products — документы.
Усреднение всех потребностей не используется: мука и упаковка — разные запросы.

## Каналы

- supplier: мои supplier-needs → чужие offers/products;
- buyer: мои offers/products → чужие supplier-needs;
- partner: мои partner-needs → чужие offers/products;
- peer: мои offers → чужие offers/products.

Buyer использует симметричный cosine уже предрассчитанной пары query/passage;
это эвристика холодного старта, не доказательство готовности компании покупать.
Для поиска query заменяет запросы канала; buyer сопоставляет текст с needs компании,
остальные роли — с предложениями. Явный поисковый запрос не смешивается с личным
вкусом и не получает канал-квоты: точное намерение важнее накопленной персонализации.

Оценка кандидата — лучший multivector match (cosine приведён к [0,1]),
вес важности/уверенности need, небольшой бонус свежести и региона, штраф повторных
**реальных** показов. Агрегация max не повышает score просто за число товаров;
однако большой каталог имеет больше шансов случайного совпадения — контролировать
на реальных данных, позже заменить top-k aggregation/порогами.
Продукты в карточке выбираются отдельно по релевантности запросу сопоставления.
Цена/остаток не бустят score: много единиц товара не означает больше пользы.

## Персональный ранкер первого этапа

Каскадные стадии отделены: `FeatureBuilder` формирует признаки пары, `SemanticRanker`
даёт cold-start baseline, `LinUCBRanker` — персональную онлайн-коррекцию,
`SlatePolicy` собирает разнообразную ленту. Переключатель: `RANKER_MODE=semantic|linucb`;
по умолчанию включён `linucb`.

Это простой ridge-linear contextual bandit, не нейросеть. Состояние каждого зрителя
изначально пустое. На событиях open, like, contact, hide и достаточном dwell обновляется
остаток награды относительно semantic baseline. Для ranking применяется
`A = λI + Σ decay * x*xᵀ`, `b = Σ decay * x * residual`, `θ = A⁻¹b`; score равен
semantic prior + персональная линейная поправка + бонус неопределённости. Старые
observations затухают; сырые события хранятся для будущего offline обучения. Impression
и отсутствие действия не становятся негативным label.

Feature snapshot сохраняется для каждого показанного кандидата: semantic similarity,
BGE percentile (нейтральный baseline при fallback), граф, freshness, география,
наличие, размер каталога, seen/novelty, intent. Версия модели и propensity выбора на
текущем шаге ленты логируются. Feature schema должна версионироваться при изменении.
Награды и параметры в `.env` — стартовые значения, не результаты обучения.

## Глобальный граф связей сегментов

`bm_relation_edges` — разреженный направленный граф, ключ ребра:
`(segment_viewer, segment_target, intent)`. Это связь «пекарня → поставщик муки»
в отдельном канале, а не неориентированная похожесть сегментов. Пока нет версионированной
таксономии, сегмент берётся из `ClientInput.segment` и нормализуется по регистру/пробелам;
это временный ключ, не попытка автоматически склеить синонимы или придумать категории.

`bm_relation_observations` хранит одно ограниченное свидетельство на выдачу,
целевую компанию и канал. При первом событии по карточке записывается одна экспозиция.
Открытие/лайк/контакт фиксируют наибольшую положительную награду; hide фиксирует
отдельное отрицательное свидетельство. Повторный event ID идемпотентен, повторные
действия на той же карточке/выдаче не раздувают глобальные веса. Экспозиция создаётся
по событию фронта, а не по самому факту построения выдачи.

Сглаженный edge-rate использует prior 0.12, силу prior 20, полураспад 60 дней.
В score он вносит максимум примерно ±0.12 и умножается на confidence, поэтому
нулевая/редкая история почти не меняет cold start, а известные успешные межсегментные
пары влияют на скоринг. Для этого MVP это онлайн-агрегат поведенческой статистики,
**не** обученная модель параметров и не causal conversion rate: экспозиции не имеют
известной propensity, а «показано» фронт сообщает с порогом видимости.

Сначала использовать как подсказку при ранжировании, не как жёсткий фильтр и не как
генератор кандидатов: семантический retrieval всё ещё решает, какие конкретные товары
подходят. Перед продом заменить сегмент на управляемые `segment_id`/таксономию,
проверить синонимы и миграцию, добавить отчёт coverage/reliability и защиту от
популярностного feedback loop. Структуру можно позже обобщить до typed graph с узлами
товаров/клиентов/городов без смены интерфейса оценки ребра.

Далее MMR-подобный штраф близких векторов, повторов сегмента, дефицит каналов.
Около 10% решений выбирают случайный вариант внутри eligible candidate pool.
Это exploration внутри retrieval, не равномерное исследование всего каталога.

## Реранкер, freshness и exploration

BGE применяется к top-K после retrieval для feed и search, с отдельным флагом feed.
Каждый cross-encoder input — конкретная пара need/query и offer/product. Результаты
переводятся в percentile внутри rerank batch, logits не трактуются как вероятности.
При недоступности — semantic fallback. BM25, typo matching, ANN/pgvector и
collaborative filtering пока не реализованы. Направленный граф сегментов реализован
как слабый global prior.

Двухэтапная архитектура retrieval → ranking сохранена, как практический принцип,
но не воспроизводит нейросетевую систему YouTube и не требует истории на запуске.
Для полноценного обучения нужны реальные экспозиции и отложенные действия.
Позиция и вероятность выбора на текущем шаге slate policy логируются; это пока не
полная propensity всего slate и не готово для IPS. Causal evaluation потребует
отдельно спроектированной randomized policy.

## Проверка на реальных данных

1. Проверить профиль и top выдачи нескольких разных сегментов, особенно направление buyer.
2. Просмотреть качество карточек без каталога, товары с неизвестным/нулевым остатком.
3. Подать последовательность open/like/contact и сравнить ленту и каналы до/после.
4. Проверить, что hide исчезает, повторы доставки не усиливают профиль.
5. Замерить p50/p95, вызовы и TPM моделей, долю fallback реранкера.
6. После накопления: contact/open на реальную экспозицию, category coverage,
   повторяемость, diversity, новые поставщики; разрезы по позиции и сегменту.

Сейчас нет утверждения о качестве на данных: каталог и реальные API ещё не подключены.

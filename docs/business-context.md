# Контракты и платежи: реализованный MVP

Дополнительный аудит качества: `quality-audit.md`. В поиске без `intent`
теперь выбираются поставщики; остальные роли задаются явно. В обычной ленте
смешивание ролей сохраняется. В поиске нет квоты разных отраслей; товары
на карточке отбираются по близости к лучшему товарному совпадению
(`CARD_PRODUCT_SCORE_TOLERANCE`), а не просто дополняются до трёх позиций.

Проверка 26 ноября 2026: 26 pytest-тестов и 43 сценарные проверки проходят,
Ruff и pip check без ошибок. На синтетическом каталоге из 803 компаний
поставщики муки после нового договора: 0 → 12 в top-20; после смены темы
поставщики печей: 0 → 12. Проверены возврат к прежнему интересу, hide,
изоляция пользователей, дубли/отмены, восстановление после перезапуска,
конкурентные версии snapshot и сбои embedding/reranker. Эти числа описывают
контролируемый сценарий, а не метрики качества на реальных клиентах.
Полный локальный отчёт: `local_experiments/20261126-122350-context/`.

В `PUT /v1/clients/{id}` добавлено необязательное, write-only поле
`business_context`. Feed/search/events сохраняют прежние входные схемы.
В рекомендациях есть дополнительное поле `insights: list[str]` для UI.

Пример ниже иллюстративный; даты и идентификаторы заменяются данными источника:

```json
{
  "id": "bakery-1",
  "name": "Пекарня",
  "business_context": {
    "source_id": "erp",
    "source_sequence": 1,
    "records": [{
      "id": "contract-line-17",
      "kind": "contract",
      "role": "buyer",
      "subject": "Поставка пшеничной муки",
      "purpose": "trade",
      "status": "active",
      "occurred_at": "2026-11-20T09:00:00Z",
      "transaction_group_id": "purchase-17"
    }]
  }
}
```

## Обновление

- Остальные поля карточки по-прежнему полный snapshot, включая `products`.
- Отсутствие `business_context` сохраняет ранее загруженные источники.
- `records: []` очищает только данный `source_id`; `null` отклоняется (422).
- До 200 записей на источник, до 8 источников по умолчанию.
- `source_sequence` растёт; повтор той же версии/содержимого идемпотентен.
  Старая версия или изменённое содержимое при прежней версии дают 409.
- ID записей уникальны внутри источника; порядок записей несущественен.
- Даты требуют timezone; будущий `occurred_at` отклоняется.
- Contract: active/completed/cancelled; transfer: pending/settled/refunded.
- Role: buyer/seller/unknown относительно клиента; purpose: trade/noncommercial/unknown.
- `valid_until` и `transaction_group_id` необязательны.

Приём синхронный: факты и готовый индекс публикуются в одной SQL-транзакции.
При ошибке провайдера прежний snapshot остаётся рабочим. Это single-worker MVP:
длительный ingest держит общий lock выдачи; очереди/outbox здесь пока нет.
Данные находятся в новой таблице `bm_business_contexts`, создаваемой initialize.
API предназначено для доверенного интегратора: ключ сервиса не заменяет
разграничение прав по клиентам и источникам во внешнем backend.

## Обработка

Изменённые содержательные записи идут через Pydantic AI в `extract_signal`.
Результат: subject, role, commercial, confidence. Даты, статусы и ID берутся
только из исходной записи. Извлечённые данные кэшируются отдельно от профиля
по содержимому и конфигурации провайдера. Статус не инвалидирует extraction.
Старый профиль не генерируется заново из-за нового платежа.

Закупки создают направленные need-документы, продажи — historical offer.
SKU, цены и остатки не создаются. Неясные/некоммерческие записи, низкая
уверенность и противоречие известной роли не создают поисковых документов.
В mock-режиме стандартный extractor консервативно возвращает unknown;
сценарный тест подставляет вручную написанные ответы через HTTP mock gateway.

Группа договора/платежей получает максимум поддержки по теме, не сумму.
Отмена/возврат консервативно снимает всю связанную группу. Частичные возвраты
не моделируются; source_id ограничивает область группировки. Между источниками
точной дедупликации нет, но поиск использует лучший match, а не сумму платежей.
Повторяемость отдельных сделок пока НЕ получает отдельного накопительного бонуса.

Кандидаты учитывают evidence уже до top-K. Прибавка ограничена
`BUSINESS_SIGNAL_BOOST × similarity × support`; support затухает с возрастом.
Значения 0.12 / 60 дней / 365 дней — настраиваемые стартовые настройки,
не результат калибровки на реальных пользователях. После max-age/valid-until
документ не участвует в поиске. Пока документ допустим, он также даёт
семантическую поисковую тему: затухание бонуса не равно затуханию всей темы.
Историческая покупка не доказывает открытую заявку; распознавания циклов
повторной закупки и закрытой разовой потребности в этом MVP ещё нет.

Фильтры и hide сохраняют силу; peer не использует evidence. Контракты не
создают фиктивных кликов. Только реальные события обучают личный ранкер.
Feature-layout изменён: несовместимое старое состояние игнорируется, feedback
по старым slate отклоняется — фронтенду нужно обновить ленту.

## Выдача и проверка

Raw-контекст не возвращается через GET/PUT карточки. Для evidence-совпадений
matched_need/matched_text показывают общую формулировку; insights —
«Совпадение с наблюдаемой хозяйственной деятельностью». Внешний UI отображает
эту строку как badge; frontend в этом репозитории не реализован.
Ранкер/эмбеддинг/reranker используют извлечённую тему внутри доверенного контура.

Запуск самодостаточного локального эксперимента:

```powershell
.venv\Scripts\python.exe scripts/business_context_check.py --per-family 100
.venv\Scripts\python.exe -m pytest -q
```

Каталоги, запросы, ручные extraction-ответы, ленты и SQLite сохраняются только
в игнорируемой `local_experiments/*-context/`. Импортированные `fixtures/`
тоже остаются локальными; старые архивные journey-скрипты требуют этих fixtures.
Новый business_context_check генерирует данные сам. Проверки используют
hashing embeddings и ручные, в том числе неполные/ошибочные ответы: это
проверка интеграции и поведения, а не доказательство качества реального Qwen/BGE.

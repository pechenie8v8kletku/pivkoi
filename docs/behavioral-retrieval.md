# Поведенческий отбор кандидатов

## Результат парного аудита

`local_experiments/20261126-143453-interests/`: 72 оценённых выдачи,
24 уникальных события по шести компаниям (каждое также отправлено повторно
для проверки дедупликации). В обоих режимах идентичны личные веса, история
и граф; различается только включение поведенческого отбора. Два seed.

| Клиент / текущая тема | Карточки темы, off → on | Средний NDCG@10, off → on |
|---|---:|---:|
| Пекарня / упаковка | 0 → 3 | 0.000 → 0.514 |
| Салон / косметика | 2 → 4 | 0.164 → 0.586 |
| Мебель / древесина | 4 → 4 | 0.330 → 0.630 |

В пуле компаний без обучающих действий: упаковка 0 → 1, косметика 1 → 2;
древесина остаётся 4, но её NDCG вырос 0.543 → 0.783. У мебели это улучшение
порядка при неизменном количестве, а не рост количества новых поставщиков.
Точность основной ленты по всем потребностям: пекарня 19/20 → 20/20,
салон и мебель 20/20 → 20/20. В проверочном пуле пекарни остаются
нерелевантные карточки: 16/20 → 18/20, не идеальная выдача.

Все семь технических проверок прошли: одинаковое сохранённое обучение,
сохранение порядка после рестарта, идентичный порядок явного поиска,
отсутствие обучения на проверочном пуле, отсутствие fallback BGE и новых OOM.
Основные ленты on: примерно 2.2–2.4 с в этом локальном прогоне.

Это эффект новой retrieval/сопоставляющей части при фиксированном LinUCB,
а не доказательство улучшения самого обучения LinUCB. Три синтетических
клиента, одна задача на клиента, не проверка реальной конверсии или
долгосрочной смены десяти интересов. Лимит десяти проверен отдельно
на контролируемых векторах, в этом GPU-прогоне десять тем не набирались.

## Реализованная версия

История клиента теперь участвует в отборе кандидатов ленты, до LinUCB.
До 10 представительных векторов суммарно на клиента, с разделением ролей.
Это отдельные эмбеддинги подтверждённых предложений, не один усреднённый
вектор и не PCA. Представитель сохраняет исходный текст для BGE.

- Лайк/контакт сохраняют опору на реально показанное предложение. При
  указанном product_id в supplier-канале берётся конкретный показанный SKU.
- Используются исходные эмбеддинги, без сжатия до 32 измерений для поиска.
  32-мерная проекция личного LinUCB остаётся отдельной существующей механикой.
- Сила контакта 1, лайка 0.8; затухание с half-life 14 дней. Выбор по силе
  с детерминированным разрешением равенства. Повторные действия не суммируются.
- Близкие векторы одной роли (cosine >= 0.9) объединяются выбором сильнейшего
  представителя; разные темы не усредняются. Лимит 10 действует на все роли.
- Одиночные открытия, dwell и показы не создают поисковые интересы в этой
  версии. Существующее обучение LinUCB на этих событиях работает отдельно.
- После hide прежние положительные действия по компании/роли не оживают
  автоматически. После истечения hide новый подтверждённый интерес допустим.
- Неактивный источник, удаление/изменение исходного документа, исчезновение
  доступного SKU или смена embedding-модели/endpoint отзывают этот anchor.
  Это консервативный выбор: интерес не переносится автоматически на новую
  редакцию товара. Для изменения этого поведения потребуется явная миграция.

На каждый вектор до 20 кандидатов, с отдельным относительным порогом.
Исходный пул профиля считается независимо и объединяется с поведенческими.
Один пагинированный проход каталога обслуживает все пулы; число векторных
сравнений увеличивается. Лучшая пара запроса/документа выбирается для компании
и роли. Итоговый размер ленты и её разнообразие по-прежнему определяет slate-policy.
Сохранение исходного пула не гарантирует наличие всех старых тем на странице.

При явном поиске поведенческие пулы не добавляются. Личные веса по-прежнему
могут сортировать кандидатов явного запроса. Диагностика interest_candidates
считает кандидатов, чья выбранная пара пришла из поведенческого пула;
это не обязательно число новых компаний относительно исходного пула.

## Совместимость и ограничения

API событий и структура публичных карточек сохраняются. В SQL JSON слейтов
и событий добавлены внутренние interest_anchor/product_anchors. Текст, вектор
и идентификатор embedding-провайдера закреплены за показом. Evidence-документы
не сохраняются как поведенческие anchors, чтобы не переносить частный контекст.
Старые события без anchors не мигрируются догадками, но работают для прежних
личных весов. При новом действии на новой выдаче появляется полноценный anchor.

Это не вся архитектура краткосрочного/долгосрочного профиля: отдельного
сессионного состояния, накопления поддержки от нескольких действий, новых
контекстных признаков LinUCB и обучения PCA здесь нет. Правила силы/порогов
стартовые и на независимой выборке пока не откалиброваны.

SQL-история читается для каждого запроса ленты; вектора хранятся в JSON.
Объём исходной истории и линейный точный поиск остаются ограничениями MVP.
Для большого трафика нужны материализованный профиль интересов, индекс ANN
и обновление профиля по событию. Поиск всё ещё не имеет калиброванного
абсолютного порога «ничего не найдено».

## Проверка

Unit/API тесты: новые соседи после контакта, сохранение исходного пула,
отсутствие расширения явного поиска, изоляция клиентов и ролей,
дедупликация, лимит 10, hide, истечение, изменение каталога и модели.

```powershell
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe scripts/interest_audit.py --source local_experiments/20261126-131536-real-models/service.db --fixtures local_experiments/20261126-123951-quality
```

Аудит создаёт свежую обучающую БД, отправляет настоящие HTTP-события и
клонирует полученное состояние для двух режимов: interest retrieval off/on.
Таким образом веса LinUCB, граф и история одинаковы; меняется только новый
отбор. Используются реальные Qwen/BGE и синтетические метки; генерация
профиля остаётся контролируемой. Ответы, события и проверки сохраняются
в игнорируемой local_experiments/*-interests/. Результаты описываются
только после завершения прогона.

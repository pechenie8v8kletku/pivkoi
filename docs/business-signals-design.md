# Контракты и переводы: предложение интеграции

**Обновление:** MVP реализован. Действующий контракт и ограничения описаны
в `business-context.md`; разделы ниже сохраняют историю проектирования.
Очередь/outbox, накопительный бонус повторяемости и отдельный ingest endpoint
из первоначального проекта в текущую реализацию не входят.

## Уточнение MVP после переноса архива в основную репозиторию

Для первого этапа с минимальной правкой внешней спеки предлагаем optional
`business_context` в существующем `PUT /v1/clients/{id}`. Объект содержит
`source_id`, монотонный `source_sequence` и `records` нормализованных контрактов
и платежей. Отсутствие поля сохраняет ранее загруженный контекст; явный пустой
`records` очищает только указанный источник. `null` отклоняется как неоднозначный.
Обновление и проверка версии выполняются атомарно. Это явно документируемое
исключение из полного snapshot карточки; старые отправители не стирают контекст.

Внутренне данные всё равно хранятся отдельно от каталога и публичного source.
Текущий `GET /clients/{id}` нельзя расширять выдачей исходного закрытого контекста.
Qwen получает изменившиеся содержательные записи и возвращает отдельные
`search_signals`: предмет, роль клиента, source_refs и тип вывода. Статусы и даты
копируются из источника и валидируются сервером. Приоритет задаёт ограниченная
политика с давностью и дедупликацией, а не произвольный priority от LLM.
Раздельный endpoint ниже остаётся следующим шагом для независимого ingest.
Этот раздел уточняет предпочтительный MVP; реализация пока не выполнена.

Статус: проект решения, не реализованный API. Основа — krutota.zip из
Downloads/Telegram Desktop, распакованный 26 ноября 2026. Под переводами
ниже понимаются денежные платежи между компаниями. Реального образца данных
контрактов/платежей пока нет; названия полей необходимо сверить с источником.

## 1. Решение

Хранить подтверждающие бизнес-факты отдельно от products и click feedback.
Использовать их для создания дополнительных поисковых документов, ограничения
неопределённости профиля и ограниченного повышения релевантных рекомендаций.
Не повышать все рекомендации компании только потому, что у неё есть платежи.

Пример: пекарня перечислила оплату за муку. Это историческое свидетельство
закупки муки пекарней и продажи муки контрагентом, а не предложение пекарни
продавать муку. Оно не доказывает новую закупочную потребность, наличие товара
на складе контрагента или удовлетворённость покупателя.

## 2. Минимальное расширение API

Предпочтительно добавить один endpoint:

PUT /v1/clients/{client_id}/business-signals

Существующие PUT карточки, feed, search и events сохраняют свои request-схемы.
Отдельный endpoint позволяет карточке и бухгалтерским данным обновляться
независимо; старый отправитель полного snapshot не удалит новые сигналы.
Он принимает полный snapshot нормализованных сигналов для одного источника.
Пустой items очищает только этот источник; остальные источники сохраняются.
Повтор той же revision и того же содержимого — no-op; та же revision с другим
содержимым — конфликт. source_sequence — монотонный номер snapshot на стороне
интегратора, меньшие значения отклоняются, чтобы задержанный snapshot не
восстановил отменённые факты. Права на source_id выдаются интегратору сервером.

Иллюстративный payload, не реальные данные:

```json
{
  "source_id": "erp",
  "source_sequence": 42,
  "revision": "snapshot-42",
  "items": [
    {
      "id": "purchase-line-1",
      "kind": "contract",
      "role": "buyer",
      "subject": "Мука пшеничная для производства хлеба",
      "status": "active",
      "occurred_at": "2026-11-20T09:00:00Z",
      "valid_until": "2026-12-20T00:00:00Z",
      "counterparty_client_id": "mill-17",
      "transaction_group_id": "purchase-1"
    },
    {
      "id": "payment-1",
      "kind": "transfer",
      "role": "buyer",
      "subject": "Оплата муки по purchase-1",
      "status": "settled",
      "occurred_at": "2026-11-21T09:00:00Z",
      "counterparty_client_id": "mill-17",
      "transaction_group_id": "purchase-1"
    }
  ]
}
```

role — роль клиента в хозяйственной операции, не intent выдачи. Разрешён
unknown: направление денежного потока само по себе не определяет покупателя
и продавца. Возвраты, займы, налоги, зарплаты, собственные переводы и комиссии
не считаются закупками. Enum статусов валидируется отдельно для каждого kind.
counterparty_client_id необязателен; связь только по проверенному идентификатору,
не по похожему названию. Без связи всё ещё можно использовать предмет закупки.
Отменённые/возвращённые операции отзывают поддержку, но не означают dislike.

Если новый маршрут невозможен, запасной вариант — optional business_signals
в ClientInput. Для него придётся отдельно определить: отсутствие = сохранить,
items=[] = очистить, плюс source/revision. Это исключение из полного snapshot
карточки, поэтому отдельный endpoint проще и безопаснее для интеграции.

## 3. Что передавать и где хранить

Сырые PDF, выписки, реквизиты и весь платёжный поток остаются в системе-источнике.
Интегратор выделяет относящиеся к бизнесу позиции и передаёт нормализованные факты.
Каждый факт хранит источник, внешний ID, версию, время операции, статус и
ссылку на группу сделки; сумма/валюта могут храниться как закрытые атрибуты
при реальной необходимости, но в первой версии не нужны для ранжирования.
Нельзя сравнивать суммы разных валют или автоматически давать крупным платежам
неограниченный приоритет. Лимит snapshot, окно истории и объём текста настраиваются.
Для большой истории следующий этап — отдельный идемпотентный delta/batch ingest.

Предлагаемые таблицы: bm_business_signal_sources (ревизия snapshot),
bm_business_signals (факты) и bm_business_insights (агрегаты/выделенные темы).
Источник, клиент и ID образуют уникальный ключ. Snapshot применяется транзакционно;
обновление индекса через outbox/задачу с ревизией. Устаревшая задача не публикует
новую версию индекса. Ответ ingest: accepted_revision, changed, indexing_status.
До завершения обработки выдача использует последнюю завершённую ревизию.
Это проект следующей реализации; очереди/outbox в текущем архиве нет.

## 4. Что делает Qwen

Qwen через существующую Pydantic AI обвязку выделяет предмет, категории и
роль только там, где это не удалось надёжно нормализовать заранее. Отдельная
типизированная схема результата содержит subject, role, source_refs и
extraction_confidence. Даты, статусы, суммы и идентификаторы берутся из
источника, а не придумываются моделью. Неподтверждённая роль остаётся unknown.
Самооценка уверенности LLM не равна вероятности достоверности факта.

Обработка запускается при смысловом изменении сигнала, кэшируется по
нормализованному содержимому и версии extractor. Изменение статуса отзывает
документ без нового LLM-вызова. Feed и клики не вызывают LLM повторно.
Оригинальные business-signals не следует просто включать в source.model_dump()
основного профиля: иначе каждый платёж инвалидирует весь профиль и создаст
дорогие вызовы вместо независимого обновления сигналов.

## 5. Направления поиска

| Факт о клиенте | Для его ленты | Для других клиентов |
|---|---|---|
| Закупает муку | Дополнительная need/supplier по муке | Возможный buyer для продавца муки |
| Поставляет печи по договору | Историческое offer для поиска покупателей | Возможный supplier для нуждающихся в печах |
| Перевод без ясного назначения | Не создавать товарную потребность | Не давать предметный boost |

Сделку использовать как наблюдение о прошлой деятельности, а не автоматически
как открытую заявку. Периодические закупки могут поддерживать устойчивый интерес;
разовая покупка оборудования может уже закрыть потребность. Просроченные и
завершённые договоры теряют вес по отдельным правилам. Действующий договор
не гарантирует доступность нового заказа. Правила по времени/статусу — конфигурация,
а не таблица конкретных отраслей.

products оставляем реальным каталогом: из финансового факта не создаём SKU,
цену или остаток. Исторические offers должны иметь provenance и не показываться
как подтверждённое наличие. Сигналы buyer не используются как peer-описание.

## 6. Приоритет и обучение

Поддержка агрегируется по клиенту, роли и предмету. Договор и платежи по нему
объединяются через transaction_group_id; платежи частями не становятся множеством
независимых подтверждений. Если связи нет, не притворяться, что надёжная дедупликация
выполнена: ограничивать суммарный вклад темы и сохранять неопределённость.

Схема начального сигнала:
support = source_reliability × extraction_quality × status_factor × time_decay
evidence_boost = configurable_cap × matched_subject_relevance × aggregated_support

Это конфигурируемый prior, не обученная магия. Значения и пороги нужно выбрать
по данным; сейчас никаких числовых весов по умолчанию не обосновываем. Учёт
повторяемости насыщается, источники и темы ограничены. Знакомый контрагент может
иметь отдельный ограниченный признак связи, но не монополию на выдачу.

Подтверждённые темы должны участвовать уже в candidate retrieval: boost после
top-K не вернёт компанию, отсеянную раньше. Нужен объединённый ограниченный пул
обычных и evidence-кандидатов с дедупликацией, затем общее ранжирование.
Сохраняются hard filters, hide, релевантность, разнообразие и exploration.

Добавить признаки support/recency/repeat/source/relation в снимок признаков
ранкера. Исторический контракт не записывается как фиктивный click/contact: у
него нет decision-time slate и вероятности показа. Личный ранкер продолжает
учиться на настоящих событиях; при изменении признаков версия обновляется.
Для отключения: BUSINESS_SIGNALS_ENABLED=false и нулевой evidence boost.
Действительный источник и выдача с инсайтами должны проверяться отдельной абляцией.

## 7. Подсветка в ответе

feed/search request не меняются. Для простого интерфейса можно заполнить уже
существующий reason фразой «Есть подтверждённый интерес к этой категории».
Для надёжного badge добавить optional insights=[] в Recommendation:

```json
{
  "insights": [{
    "code": "observed_category_demand",
    "subject": "Мука",
    "label": "Есть подтверждённый интерес к категории"
  }]
}
```

Подсветка зависит от конкретного совпадения и доступности объяснения вызывающей
стороне. Сырые суммы, назначение платежа, номер договора и контрагент не включаются
в общедоступную карточку. Чужие закрытые факты не должны попадать и в matched_text:
для поиска нужен отдельный публично допустимый текст документа и приватный provenance.
Текущий GET /clients/{id} возвращает source целиком, поэтому сырые бизнес-факты
не стоит помещать туда без разграничения доступа.

## 8. Точки изменения в архиве

- schemas.py: отдельные BusinessSignalSnapshot/BusinessSignal/Insight;
  существующий Product не меняется.
- app.py/storage.py: один новый ingest endpoint и независимое хранилище.
- отдельные extractor/aggregator: источники → темы с provenance.
- indexing.py: инкрементальный слой evidence-документов, отдельная ревизия.
- retrieval.py: направленные evidence-документы и объединение candidate pools.
  Сейчас документ цели в buyer-поиске не взвешивается по evidence; просто
  увеличить Need.importance недостаточно.
- ranking.py/engine.py: ограниченный evidence prior, признаки, версия, safe explanations.
- integration.md/openapi.json: документировать добавления и совместимость.

В архиве providers.py уже содержит исправления шлюза (metadata.weight_versions,
повтор структурированного ответа и BGE /score). Эти изменения сохранять при
реализации; не заменять файл версией из текущей рабочей папки.

## 9. Проверки перед включением

1. Старые payload работают; обновление карточки не стирает сигналы.
2. Покупка муки не превращает пекарню в продавца муки.
3. Договор плюс несколько платежей учитываются одной группой подтверждения.
4. Повтор snapshot ничего не меняет; старый snapshot не отменяет новый.
5. Отмена/возврат отзывает поддержку; нет ложного dislike.
6. Unknown-платежи и некоммерческие операции не порождают закупки.
7. Подтверждённая релевантная тема попадает в пул; нерелевантная богатая компания
   не получает глобальный boost.
8. Hide и фильтры сильнее evidence; альтернативные компании остаются в ленте.
9. Источник отозван — агрегат и индекс перестроены; повторный LLM-вызов не нужен
   для изменения только статуса.
10. GET/feed/search/logs не раскрывают закрытые исходные факты.
11. Сравнение signals off/on на независимых сценариях и событиях пользователей.

До реализации нужен обезличенный пример контракта и перевода: какие есть поля
роли сторон, назначения, дат, статусов, связи платежа с договором и ID контрагентов.
Архив содержит код, но такой формат входных данных пока не установлен.
